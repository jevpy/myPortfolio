# Activate daily editorial reading refreshes

The workflow retains all eligible recent, topic-relevant publisher links found within bounded discovery at **08:37 UTC daily**, validates them, and pushes only `src/data/hacker-news.json` to the repository's actual default branch. HN Algolia, DEV.to/Forem and selected InfoQ feeds are internal discovery sources, not UI aggregator branding. Publishing this workflow is a separate human decision: **nothing is activated, committed, pushed, or deployed by this local implementation**. The M1 local live mixed-source refresh already succeeded across all three providers and seeded source data only; it did not activate automation.

## Quick path — after review and publication

1. Publish the reviewed workflow, updater, schema, tests, and snapshot on the default branch. Ensure Actions is enabled and repository/organization policy allows the job's `contents: write` token. Branch protections or rulesets must permit its bot push; otherwise the run fails safely. Do not weaken protections without review.
2. In Vercel, confirm the linked repository and project's **Production Branch** match the intended default branch. Check Git integration access and any Ignored Build Step: it must not skip changes confined to this JSON file. Integration behavior is not verified by local tests.
3. In GitHub Actions, select **Update editorial reading → Run workflow** on the default branch for the first refresh. Manual runs on other branches are skipped. There are no push or pull-request triggers.
4. Check the successful run and bot snapshot commit: expect all eligible unique article IDs found, with no total, source or category cap, and an actual `updatedAt` refresh-clock timestamp. Sparse results and zero articles are valid successes; this timestamp is internal and not displayed. Each `eventAt` is interpreted according to `dateKind`: HN uses submission time, not verified publisher publication time; DEV and InfoQ use source-reported publication time. Original-language source titles are preserved in JSON; sources are not guaranteed to be English.
5. **Verify deployment separately** in Vercel, then open `/blog` and `/es/blog`: confirm only currently eligible links appear, six localized primary-category filters and separate tags work, and empty results are honest. Article title, domain and source CTA links open a new tab with `noopener noreferrer` and an accessible localized notice; authored cards retain their internal destinations but also open a new tab. Navigation, back and filter links stay same-tab. No discovery-service branding, discussion links, rankings or refresh timestamps should appear in UI or descriptive metadata. A successful Git push or hook response is not proof of a successful production deployment.

## Deployment choices

| Route | What to verify |
| --- | --- |
| Git integration only (default) | Vercel recognizes the commit, allows its author/repository context, selects the correct branch, and does not ignore the build. Without a hook, the workflow explicitly reports integration-only operation; activation is not guaranteed. |
| Optional Deploy Hook | After a successful JSON push only, the workflow makes one bounded POST to the configured hook. This can request a build if Git integration does not trigger one; it is not a fallback retry after a failed push. If both routes work, duplicate builds may result. |

The commit uses the truthful `github-actions[bot]` identity, never a human author. Vercel Hobby bot acceptance depends on repository ownership, access, and integration context. Private repositories and organization-owned repositories have plan/access restrictions; check current Vercel documentation and project settings rather than assuming Hobby permits this arrangement. Hook availability and deployment eligibility also depend on the project and plan. A Deploy Hook is not permission to bypass plan restrictions.

### Optional hook setup — future human action

1. In the correct Vercel project, open **Dashboard → Settings → Git → Deploy Hooks**.
2. Create a hook for the exact intended production/default branch. A hook is branch-bound; changing the repository default branch does not automatically retarget it.
3. Privately copy the generated HTTPS URL into a GitHub repository Actions secret named **`VERCEL_DEPLOY_HOOK`**. **Keep the complete URL secret: never send it in chat, commit it, or paste it into logs.** Rotate/delete it if exposed.
4. On a future successful refresh push, the workflow validates the fixed `api.vercel.com` host and `/v1/integrations/deploy/` endpoint, rejects credentials/query/fragment/nonstandard ports, and POSTs once with a 30-second timeout and redirects disabled. It logs neither URL nor response body. Failure is reported after the snapshot push; the commit is not rolled back.

Hook tests are purely mocked. No hook, secret, or deployment network request is used locally. No secrets need to be configured to read any of the three sources.

## Discovery and display semantics

- Schema version 4 stores namespaced IDs, `source`, `sourceId`, `dateKind` and `eventAt`. HN retains `submittedAt` with `dateKind: submitted`; DEV and InfoQ retain `publishedAt` with `dateKind: published`. These raw JSON provenance fields are internal, not UI aggregator branding. `updatedAt` records the actual refresh clock and is not displayed. Schema2 compatibility is a pure offline migration/normalization: no refetch or invented publication dates, and no lost last good snapshot on a failed first refresh.
- The rolling seven-day window applies to each source's date kind. An old publisher article submitted recently to HN can qualify; HN does not verify publisher publication time. DEV uses official `published_at`, not creation/edit time, and retains an article-eligible external `canonical_url` unchanged (including tracking and fragments). An unsafe or editorially excluded canonical destination falls back only to a recognized `dev.to/author/post` URL; if neither qualifies, the row is excluded. InfoQ uses RSS2 `pubDate`, or a valid `dc:date` fallback; conflicting dates fail validation. Publication dates are source-reported, not independently verified.
- Destination eligibility is a pure URL/title heuristic, separate from credential-free HTTP(S) transport safety, applied before topic classification and provider/global selection. Known code-forge repositories, gists, raw code, model/dataset/space pages, identifiable demo/playground routes and download files are excluded using hostname and path boundaries, not substring guesses. Actual `github.blog` articles and individual Hugging Face blog posts remain possible destinations. GitHub Pages requires an identifiable individual blog/post/article or dated-slug path (including HTML); bare roots, indexes and arbitrary project/demo pages do not qualify. Tool articles and `Show HN:` titles are not blanket-banned. Unknown external publishers remain eligible unless these rules identify a non-article destination: the heuristic cannot prove article bodies or eventual redirects, and does not guess that an entire marketing domain is a demo.
- Current `validateSnapshot` strictly rejects ineligible destinations and requires schema4's exact selection contract (`windowDays: 7`, `order: newest`, `classifierVersion: 2`), without `maxArticles` or an implicit count limit. Schema version 3 is a historical contract only: its private validator pins the original selection (`maxArticles: 10`, classifier version 2) and count ≤10. Offline schema3 normalization first validates the complete original envelope and every original row, including excluded rows: exact fields, provenance/date kind, classifier/tags, seven-day window, order and duplicates. Only then does it filter destinations, migrate to schema4 and strictly revalidate the result. Malformed excluded rows invalidate the entire snapshot, never disappear through per-row error catching. Retained metadata, original URLs, ordering and `updatedAt` values stay unchanged; schema2 migration returns schema4 and screens destinations without inventing publication dates. Classifier version 2 and the six-category taxonomy are unchanged.
- Historical schema3 migration retained eligible article objects, ordering and the original timestamp without a fresh fetch or freshness claim. The older ten-to-eight destination-exclusion case is covered by deterministic historical fixtures, not mutable live seed identities. This weekly-popularity/pagination implementation does not refresh source JSON. Independent live refresh, retest, rebuild and SSR verification remain follow-up P2 work; the earlier uncapped U2 verification is unreconciled, not claimed complete.
- Six primary categories: AI Engineering, Software Architecture, Web Development, Automation Integrations, Cloud DevOps, Security. General AI, Agents and Harnesses are separate evidence-backed tags, not primary filters. The conservative title/explicit URL-path/source-tag classifier version 2 never uses hostname, query parameters, summaries or article bodies as evidence. Unmatched candidates are excluded; generic games need qualifying engineering/tooling evidence. Category precedence is Security → AI Engineering → Automation Integrations → Cloud DevOps → Software Architecture → Web Development, with at most five category matches retained.
- HN Algolia `search_by_date` uses story-only title searches and `created_at_i` bounds: 25 queries, at most two pages and 100 hits per page, up to 5,000 raw candidates, 50 logical requests and 150 requests including three attempts. Pagination can stop earlier; coverage is not exhaustive.
- DEV's public `/api/articles` endpoint scans nine tags (`ai`, `machinelearning`, `architecture`, `webdev`, `n8n`, `oauth`, `integrations`, `devops`, `security`), at most two pages of 100 articles per tag (18 logical requests, up to 54 attempts). It sends `Accept: application/vnd.forem.api-v1+json`. Every request includes `top=7`: official Forem V1 defines this as most-popular articles published in the last seven days, alongside exact `tag`, `page` and `per_page` filters. This is provider-native weekly popularity for DEV only, not a locally calculated reaction order, reaction minimum, top-N quota or cross-provider score. Every row's `published_at` is still explicitly filtered for the rolling seven-day window, future dates and category eligibility; response order is not treated as chronological. HN and InfoQ discovery criteria are unchanged; the mixed feed remains globally newest-first.
- InfoQ reads three fixed feeds: [Architecture](https://feed.infoq.com/architecture/), [AI Development](https://feed.infoq.com/ai-development/) and [AI Architecture](https://feed.infoq.com/ai-architecture/). Three logical requests allow up to nine attempts. A maintained `fast-xml-parser` 5.11.2 dependency validates RSS2; DTD/ENTITY declarations and unknown entities are rejected, only safe predefined/numeric entities are decoded, and no external entities are resolved. Limits per feed: depth 24, 500 items, 65,536 characters per text/attribute value and a 1 MiB response. Article titles are capped at 1,000 characters across sources. GUIDs are opaque identity only; article bodies, enclosures and GUID destinations are never fetched.
- Global selection sorts by newest `eventAt` with deterministic ID tie-breaking, deduplicates namespaced IDs and cross-source canonical publisher URLs, then retains ALL eligible articles found, without truncation. Known tracking parameters and fragments are ignored for comparison only; the stored original URL remains unchanged. No source or category quotas or filler are used. A provider can contribute zero articles despite successful fetching. There is no guaranteed source balance. Network discovery limits bound what is found, not a user-visible article quota; coverage is not exhaustive all-provider indexing. Sparse results and zero articles are valid successes, not evidence of a source failure.
- There is no article-body or originality verification, scraping, fabricated summary, image or translation. Original-language titles remain intact; source language is not guaranteed to be English.
- Reading pagination is server-rendered with 12 links per page, a display size only, never a dataset cap. Topic filtering and full topic counts run before pagination on all recent eligible articles; no source or category quotas are added. Page numbers are unsigned positive decimal strings; invalid/zero requests resolve to page 1, huge positive requests safely clamp to the last page, and duplicate `page` queries use the first value. Empty results have page 1 and no navigation. Topic links reset pagination; page links preserve the current topic and other query values on the same pathname with `#reading`. A bounded numbered window includes first/last pages and noninteractive ellipses, localized range/page/previous/next labels, and no previous/next links beyond boundaries. Numbering follows the selected filtered newest-first set, not popularity rank. The five authored cards per locale remain separate and unpaginated. No JavaScript or infinite autoload is required. Keyboard, screen-reader and responsive browser acceptance remains pending independent checks.
- The snapshot is an accumulated history: each refresh reads the committed snapshot, keeps every stored article and adds the newly collected ones. A re-collected article replaces its stored copy by ID; canonical URL duplicates are dropped. There is no age or count limit, so the file grows over time. The seven-day window bounds collection only. A missing snapshot starts an empty history; an unreadable or invalid snapshot aborts the refresh without writing, so history is never silently erased.
- UI shows the whole accumulated history newest-first and hides only future articles according to `eventAt`, even when a refresh fails. Failure preserves the last good snapshot file.
- Original publisher URLs, including fragments and tracking parameters, remain link destinations. Display-only leading `Show HN:` and `Ask HN:` labels are removed case-insensitively; if removal leaves only whitespace, the original title is the fallback. JSON titles remain unchanged. This is not blanket text removal: actual publisher names and unrelated title wording remain. Titles use escaped text rendering, not HTML injection; hostname display accepts only credential-free HTTP(S) URLs and returns an empty fallback for invalid URLs.

## Safety and operational limits

- The top-level token permission is `contents: read`; only the refresh job requests `contents: write`. Actions are pinned to reviewed full commit SHAs and Node is 22. `npm ci --ignore-scripts --no-audit --no-fund` installs locked dependencies before all four tests and the updater; the RSS parser requires `node_modules`. Tests cover `tests/hacker-news.test.mjs`, `tests/news-sources.test.mjs`, `tests/editorial-blog.test.mjs` and `tests/hacker-news-workflow.test.mjs`.
- M1's installer reported 37 dependency vulnerabilities. This includes the existing dependency baseline and must not be attributed entirely to the new parser. A separate audit follow-up remains necessary; neither workflow runtime audits nor audit-fix/unrelated dependency upgrades are part of this refresh.
- One concurrency group serializes refreshes without cancelling an active run. The job has a ten-minute timeout. Pending-run replacement is possible; concurrency is not a durable queue.
- The updater allows only fixed HTTPS hosts `hn.algolia.com`, `dev.to` and `feed.infoq.com`, with no credentials/nonstandard ports or redirects. Streaming reads enforce the 1 MiB cap; a five-second default deadline covers headers and body together, with up to three attempts per request and bounded retry delays. HN default concurrency is four; DEV tags/pages and InfoQ feeds are sequential. All enabled sources must succeed before selection/write: any source error, malformed response or unsafe XML aborts the entire refresh and preserves the prior file bytes. A same-directory exclusive temporary file and atomic rename replace only a validated uncapped snapshot (including zero articles); no partial-source success overwrites last good data.
- Publication stages only the JSON. The remote branch tip is compared before and after the local bot commit; an intervening advance fails safely. The final push is ordinary, never forced. Retry a failed race with a fresh manual run; do not force-push.
- GitHub schedules can be delayed or dropped under load. Public-repository schedules can be disabled after **60 days of inactivity**. Inspect Actions and re-enable as needed; use the first manual run rather than waiting for the schedule.
- Pushes made with `GITHUB_TOKEN` do **not** trigger ordinary downstream Actions push workflows. Do not assume an Actions-based deploy pipeline will run; verify the separate Vercel integration/hook path.
- GitHub Actions and Vercel have usage quotas, rate limits, and billing/plan policies. Daily operation is not a guarantee of free service. Review current limits before activation and monitor builds, especially when both Git integration and a hook are enabled.

## Recovery checklist

- [ ] For a failing refresh, retain the last good snapshot file and inspect the Actions failure. The UI keeps showing the accumulated history. Do not replace missing results with invented articles.
- [ ] To pause, disable **Update editorial reading** in Actions or remove its schedule in a reviewed change. Remove/disable the Deploy Hook separately if no longer wanted.
- [ ] To roll back bad data, restore a known-good JSON through a reviewed ordinary commit, then independently verify the resulting deployment. This guide does not authorize a local rollback, push, or deployment.
- [ ] Before resuming, check branch policies, API availability, Vercel branch/access/build settings, and secret validity privately; then run manually on the default branch.
